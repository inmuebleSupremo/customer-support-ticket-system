# ResolveDesk — Domain Model & ERD Specification

**Document version:** 0.1  
**Related document:** Product Requirements Document v0.1  
**Database:** MySQL 8+  
**Persistence layer:** Spring Data JPA / Hibernate  
**Migration tool:** Flyway

---

# 1. Purpose

This document translates the ResolveDesk product requirements into a concrete domain and relational data model.

It defines:

- domain entities;
- entity responsibilities;
- fields and data types;
- relationships;
- cardinality;
- nullability;
- database constraints;
- lifecycle rules;
- deletion strategy;
- indexing strategy;
- audit behaviour;
- concurrency considerations.

This specification should be agreed before implementing JPA entities or database migrations.

---

# 2. Core Design Principles

The database model should follow several principles.

## 2.1 Business rules belong in the application

Database constraints should protect fundamental data integrity, while business rules such as permitted status transitions belong primarily in the Spring service/domain layer.

For example:

The database can ensure that a ticket has a valid status.

The Spring application must determine whether:

`OPEN → IN_PROGRESS`

is permitted while:

`OPEN → CLOSED`

is rejected.

---

## 2.2 Important business records are not physically deleted

Tickets, comments, and ticket-history records represent business activity.

They should therefore remain available after creation.

The MVP will not support hard deletion of:

- tickets;
- comments;
- ticket history.

Users will be deactivated rather than deleted.

---

## 2.3 Historical information should remain explainable

Ticket changes must be traceable.

A ticket's current state exists in the `tickets` table.

Important state changes are additionally recorded in `ticket_history`.

---

## 2.4 Application roles and states should use controlled values

The following domain concepts are finite enumerations:

- UserRole
- TicketStatus
- TicketPriority
- TicketEventType

In Java these should be enums.

In MySQL they should be stored as readable strings rather than ordinal numbers.

For example:

`IN_PROGRESS`

rather than:

`2`

This prevents changing enum ordering from corrupting persisted meaning.

# 4. Entity: User

## 4.1 Responsibility

`User` represents an authenticated ResolveDesk account.

A user has exactly one application role:

- CUSTOMER
- AGENT
- ADMIN

Users are never physically deleted in the MVP.

Accounts may instead be deactivated.

# 6. User Constraints

Database constraints:

```text
PRIMARY KEY (id)

UNIQUE (email)

email NOT NULL
password_hash NOT NULL
first_name NOT NULL
last_name NOT NULL
role NOT NULL
active NOT NULL
```

Application rules:

- email is normalized before persistence;
- self-registration always creates CUSTOMER users;
- only Administrators may change user roles;
- inactive users cannot authenticate;
- inactive agents cannot receive new ticket assignments.

Passwords are never stored directly.

Only the password hash is persisted.

# 8. Entity: Ticket

## 8.1 Responsibility

`Ticket` is the central aggregate in ResolveDesk.

It represents one customer support request and stores its current operational state.

A ticket belongs to exactly one customer.

A ticket may be assigned to zero or one support agent.

# 10. Human-Readable Ticket Number

The application requires identifiers such as:

```text
SUP-1042
```

The MVP does **not** need a second ticket-number column.

Instead, the public ticket number will be derived from the immutable database ID.

Example:

```text
database id = 1042

public ticket reference = SUP-1042
```

This avoids storing two identifiers that represent the same thing.

Benefits:

- guaranteed uniqueness;
- no separate sequence mechanism;
- no duplicated data;
- no ticket-number synchronization problems.

The application should contain a dedicated formatter/parser for public ticket references rather than scattering `"SUP-" + id` throughout the codebase.

For example:

```text
TicketReference
```

could convert:

```text
1042 → SUP-1042
SUP-1042 → 1042
```

# 13. Ticket Relationships

## Customer relationship

```text
User 1 ─────────── 0..* Ticket
       creates
```

Each Ticket must have exactly one customer.

A Customer may create any number of tickets.

Database relationship:

```text
tickets.customer_id
    → users.id
```

`customer_id` is mandatory.

---

## Assigned Agent relationship

```text
User 1 ─────────── 0..* Ticket
       assigned
```

From the Ticket perspective:

```text
Ticket → 0..1 assigned Agent
```

An unassigned ticket therefore has:

```text
assigned_agent_id = NULL
```

The foreign key itself cannot guarantee that the referenced user has an AGENT role.

The application service layer must enforce:

```text
assigned user role ∈ {AGENT, ADMIN if permitted}
```

For the MVP, normal assignment targets should be users with the `AGENT` role.

---

# 14. Ticket Creation Rules

A newly created ticket must have:

```text
customer       = authenticated customer
assignedAgent  = null
status         = OPEN
priority       = MEDIUM
createdAt      = current UTC time
updatedAt      = current UTC time
resolvedAt     = null
closedAt       = null
```

Customers cannot supply values for:

- customer;
- assigned agent;
- status;
- priority;
- timestamps.

Those values are generated or controlled by the backend.

---

# 15. Ticket Lifecycle Rules

Allowed transitions:

```text
OPEN
 │
 ▼
IN_PROGRESS
 │      ▲
 │      │ reopen
 ▼      │
RESOLVED
 │
 ▼
CLOSED
```

Also permitted:

```text
IN_PROGRESS → OPEN
```

Full matrix:

| From | To | Allowed |
|---|---|---:|
| OPEN | IN_PROGRESS | Yes |
| OPEN | RESOLVED | No |
| OPEN | CLOSED | No |
| IN_PROGRESS | OPEN | Yes |
| IN_PROGRESS | RESOLVED | Yes |
| IN_PROGRESS | CLOSED | No |
| RESOLVED | IN_PROGRESS | Yes |
| RESOLVED | CLOSED | Yes |
| CLOSED | OPEN | No |
| CLOSED | IN_PROGRESS | No |
| CLOSED | RESOLVED | No |

No transition originates from CLOSED in MVP v1.

---

# 16. Timestamp Behaviour During Status Changes

## Transition to RESOLVED

When:

```text
IN_PROGRESS → RESOLVED
```

set:

```text
resolved_at = current UTC time
```

---

## Reopening a resolved ticket

When:

```text
RESOLVED → IN_PROGRESS
```

set:

```text
resolved_at = NULL
```

The previous resolution event remains permanently recorded in `ticket_history`.

This means `resolved_at` represents the ticket's **current resolution state**, while history preserves previous resolutions.

---

## Transition to CLOSED

When:

```text
RESOLVED → CLOSED
```

set:

```text
closed_at = current UTC time
```

The ticket becomes terminal/read-only.

---

# 17. Ticket `updatedAt` Semantics

`updated_at` represents the latest meaningful activity associated with the ticket.

It should change when:

- status changes;
- priority changes;
- assignment changes;
- a comment is added.

This makes ticket sorting by recent activity useful.

Example:

```text
ORDER BY updated_at DESC
```

shows recently active tickets first.

---

# 18. Optimistic Locking

Tickets may be viewed or modified by multiple agents simultaneously.

ResolveDesk should therefore use JPA optimistic locking.

Ticket contains:

```text
version BIGINT NOT NULL
```

Java:

```java
@Version
private Long version;
```

Example scenario:

1. Agent A loads ticket version 7.
2. Agent B loads ticket version 7.
3. Agent A changes priority.
4. Database ticket becomes version 8.
5. Agent B attempts to update stale version 7.
6. The update is rejected as a concurrency conflict.

This prevents one agent silently overwriting another agent's changes.

The eventual API should convert this situation into an appropriate conflict response rather than a generic server error.

# 19. Entity: Comment

## 19.1 Responsibility

A `Comment` represents communication attached to a ticket.

Comments may be written by:

- the owning Customer;
- Agents;
- Administrators.

Comments are treated as immutable business records in MVP v1.

There is no edit or delete functionality.

# 21. Comment Relationships

```text
Ticket 1 ─────────── 0..* Comment
```

Each comment belongs to exactly one ticket.

```text
User 1 ───────────── 0..* Comment
```

Each comment has exactly one author.

---

# 22. Comment Business Rules

A comment may be added only when:

```text
ticket.status != CLOSED
```

Customers additionally require:

```text
ticket.customer_id == authenticatedUser.id
```

Agents and Administrators may comment on tickets they are authorized to access.

Comment content:

```text
minimum: 1 meaningful character
maximum: 3000 characters
```

Whitespace-only comments are invalid.

Adding a comment should also update:

```text
ticket.updated_at
```

# 23. Entity: TicketHistory

## 23.1 Responsibility

`TicketHistory` provides an immutable audit trail of important ticket state changes.

It is not the same thing as comments.

Comments represent conversation.

# 27. What Does NOT Create TicketHistory

Comments do not require duplicate history records.

A new comment already creates its own immutable database record containing:

- author;
- ticket;
- content;
- timestamp.

Creating a second `COMMENT_ADDED` ticket-history record would duplicate information without adding meaningful audit value.

---

# 28. TicketHistory Immutability

Ticket history cannot be:

- edited;
- deleted;
- directly created through public API endpoints.

History entries are created only by business operations in the backend.

For example:

```text
changeStatus()
```

should perform both:

```text
update Ticket
create TicketHistory
```

inside the same transaction.

Either both operations succeed or neither succeeds.

# 34. Agent Deactivation Rule

An inactive user cannot:

- authenticate;
- receive new ticket assignments.

If an agent is already assigned to historical RESOLVED or CLOSED tickets, those relationships may remain.

For OPEN or IN_PROGRESS tickets, the preferred administrative workflow is to reassign or unassign those tickets before the account is deactivated.

The application may reject agent deactivation while active tickets remain assigned.

Example:

```text
409 CONFLICT

"Agent has active assigned tickets and cannot be deactivated."
```

This prevents active work from becoming silently abandoned.

# 36. Search Strategy

MVP ticket search must support:

- ticket reference;
- title.

Ticket-reference search:

```text
SUP-1042
```

is parsed into:

```text
id = 1042
```

and queried using the primary key.

Title search can initially use a case-insensitive:

```sql
LIKE
```

query.

For a portfolio-scale database containing several thousand tickets, this is acceptable.

Full-text search infrastructure should not be introduced until required.

---

# 37. Constraints Versus Application Validation

Some requirements should be enforced at multiple layers.

Example:

```text
title must exist
```

should be protected by:

1. frontend validation;
2. API DTO validation;
3. database NOT NULL constraint.

But a rule such as:

```text
OPEN cannot transition directly to CLOSED
```

belongs primarily in domain/service logic because it represents business behaviour rather than static relational validity.

# 39. Transaction Boundaries

Business operations involving history should be transactional.

Example: status change.

```text
BEGIN TRANSACTION

validate transition

update tickets.status

update tickets.resolved_at if required

update tickets.updated_at

insert ticket_history

COMMIT
```

If the history insert fails:

```text
ROLLBACK
```

The ticket must not change without its associated audit event.

The same principle applies to:

- priority changes;
- assignment changes;
- reopening;
- closure.

---

# 40. Aggregate Boundary

From a domain perspective, `Ticket` should be treated as the main aggregate.

Operations such as:

```text
assignAgent()
changeStatus()
changePriority()
addComment()
```

operate in relation to a Ticket.

Controllers should therefore not contain raw logic such as:

```text
ticket.setStatus(request.status());
repository.save(ticket);
```

Instead, a service/domain operation should validate the requested change and perform the associated history logic.

Conceptually:

```text
TicketService.changeStatus(...)
TicketService.assignAgent(...)
TicketService.changePriority(...)
CommentService.addComment(...)
```

---

# 41. JPA Relationship Guidance

Conceptually:

```text
Ticket
    ManyToOne User customer

Ticket
    ManyToOne User assignedAgent

Comment
    ManyToOne Ticket ticket

Comment
    ManyToOne User author

TicketHistory
    ManyToOne Ticket ticket

TicketHistory
    ManyToOne User actor
```

Collections such as:

```text
ticket.getComments()
ticket.getHistory()
```

should not automatically load massive datasets.

Avoid relying on large bidirectional `@OneToMany` collections with eager loading.

Comments and history should normally be retrieved through dedicated repository queries with appropriate ordering and pagination where necessary.

Default toward:

```text
LAZY
```

relationships.

---

# 42. DTO Boundary

JPA entities must not be returned directly from REST controllers.

The API should use DTOs such as:

```text
TicketSummaryResponse
TicketDetailResponse
CommentResponse
TicketHistoryResponse
UserSummaryResponse
```

This prevents:

- accidental data exposure;
- circular serialization;
- persistence-model coupling;
- uncontrolled lazy loading;
- leaking password fields or internal state.

---

```text
ticket_watchers
```

Adding unused tables because they might be useful later would make the architecture unnecessarily speculative.

They can be introduced through future Flyway migrations when genuine requirements exist.

# 47. Final MVP Relational Model

The MVP database therefore remains intentionally compact:

```text
users
  │
  ├──────────────┐
  │              │
  ▼              ▼
tickets       comments
  │              ▲
  │              │
  └──────┐       │
         ▼       │
   ticket_history
```

More precisely:

```text
users
 ├──< tickets.customer_id
 ├──< tickets.assigned_agent_id
 ├──< comments.author_id
 └──< ticket_history.actor_user_id

tickets
 ├──< comments.ticket_id
 └──< ticket_history.ticket_id
```

Only four primary tables are necessary to implement the complete MVP ticket workflow.

# 48. Model Acceptance Criteria

The domain model is considered ready for implementation when the team agrees that:

- every PRD requirement can be represented by the model;
- no MVP entity lacks a clear purpose;
- user ownership is explicit;
- agent assignment is optional;
- status and priority have controlled values;
- ticket lifecycle timestamps have defined behaviour;
- comments are immutable;
- audit history is immutable;
- deletion rules preserve historical records;
- foreign-key behaviour is defined;
- critical query indexes are identified;
- concurrent ticket updates are protected;
- ticket references have a clear strategy;
- JPA entities will not be exposed directly through the REST API.

At that point the schema can safely be translated into Flyway migrations and JPA entities.
