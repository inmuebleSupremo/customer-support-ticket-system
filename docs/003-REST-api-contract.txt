# ResolveDesk — REST API Contract

**Document version:** 0.1  
**Related documents:** PRD v0.1, Domain Model & ERD Specification v0.1  
**API style:** REST/JSON  
**Base path:** `/api/v1`  
**Backend:** Spring Boot  
**Authentication:** Spring Security authenticated session for MVP  
**Content type:** `application/json`

---

# 1. Purpose

This document defines the HTTP contract between the ResolveDesk frontend and backend.

It specifies:

- API routes;
- allowed roles;
- request DTOs;
- response DTOs;
- query parameters;
- validation behaviour;
- HTTP status codes;
- error responses;
- pagination;
- authorization behaviour;
- optimistic-concurrency handling.

Controllers and frontend API clients should be implemented from this contract rather than inventing endpoint behaviour during development.

---

# 2. API Design Principles

## 2.1 Versioned API

All business endpoints use:

```text
/api/v1
```

Example:

```text
GET /api/v1/tickets
```

This provides a clean future migration path without introducing unnecessary complexity now.

---

## 2.2 JSON Naming

JSON fields use camelCase.

Example:

```json
{
  "assignedAgent": null,
  "createdAt": "2026-09-29T10:35:00Z"
}
```

Database columns remain snake_case.

---

## 2.3 Dates and Times

All timestamps are returned as ISO-8601 UTC values.

Example:

```text
2026-09-29T10:35:00Z
```

Clients may convert them to the user's local timezone for display.

---

## 2.4 Entities Are Never Returned Directly

REST controllers must return DTOs.

JPA entities are internal persistence objects and must never form the public API contract.

---

# 3. Authentication Model

For MVP v1, ResolveDesk will use Spring Security with server-managed authenticated sessions.

After successful authentication, the backend creates an authenticated session.

The browser receives a secure session cookie.

Frontend JavaScript should not manually store passwords or authentication secrets.

The authenticated user's identity is always derived from the Spring Security context.

The client must never be able to impersonate another user by supplying:

```text
customerId
authorId
actorUserId
```

for operations where those values should come from authentication context.

---

# 4. Authentication Endpoints

## POST `/api/v1/auth/register`

Creates a new Customer account.

### Access

Public.

### Request

```json
{
  "firstName": "Alex",
  "lastName": "Morgan",
  "email": "alex@example.com",
  "password": "ExamplePassword123!"
}
```

### Validation

`firstName`

- required;
- max 100 characters.

`lastName`

- required;
- max 100 characters.

`email`

- required;
- valid email;
- max 254 characters;
- unique.

`password`

- required;
- must satisfy the configured password policy.

### Important rule

The client cannot submit:

```json
{
  "role": "ADMIN"
}
```

Self-registration always creates:

```text
CUSTOMER
```

### Success

```text
201 Created
```

### Response

```json
{
  "id": 17,
  "firstName": "Alex",
  "lastName": "Morgan",
  "email": "alex@example.com",
  "role": "CUSTOMER",
  "active": true,
  "createdAt": "2026-09-29T10:00:00Z"
}
```

Registration does not automatically grant another role.

# 5. POST `/api/v1/auth/login`

Authenticates an existing user.

### Access

Public.

### Request

```json
{
  "email": "alex@example.com",
  "password": "ExamplePassword123!"
}
```

### Success

```text
200 OK
```

The backend establishes the authenticated session.

### Response

```json
{
  "user": {
    "id": 17,
    "firstName": "Alex",
    "lastName": "Morgan",
    "email": "alex@example.com",
    "role": "CUSTOMER",
    "active": true
  }
}
```

### Failure

Invalid credentials:

```text
401 Unauthorized
```

Inactive account:

```text
403 Forbidden
```

The authentication response should not reveal whether a specific email address exists.

# 10. POST `/api/v1/tickets`

Creates a new support ticket.

### Access

CUSTOMER

### Request

```json
{
  "title": "Unable to reset my password",
  "description": "I requested a password reset several times but no email has arrived."
}
```

The client does **not** provide:

- customer ID;
- ticket ID;
- status;
- priority;
- assignee;
- timestamps.

The backend derives these values.

### Server defaults

```text
customer = authenticated user
status = OPEN
priority = MEDIUM
assignedAgent = null
```

### Success

```text
201 Created
```

The response should include a `Location` header such as:

```text
/api/v1/tickets/1042
```

### Response

```json
{
  "id": 1042,
  "reference": "SUP-1042",
  "title": "Unable to reset my password",
  "description": "I requested a password reset several times but no email has arrived.",
  "status": "OPEN",
  "priority": "MEDIUM",
  "customer": {
    "id": 17,
    "displayName": "Alex Morgan"
  },
  "assignedAgent": null,
  "createdAt": "2026-09-29T10:35:00Z",
  "updatedAt": "2026-09-29T10:35:00Z",
  "resolvedAt": null,
  "closedAt": null,
  "version": 0
}
```

# 11. GET `/api/v1/tickets`

Returns a paginated ticket list.

The data visible through this endpoint depends on the authenticated role.

### CUSTOMER

Returns only tickets where:

```text

```

### AGENT

Returns the complete support queue.

### ADMIN

Returns the complete support queue.

Authorization filtering must occur on the backend.

# 18. Resource Access Behaviour

If ticket `1042` exists but belongs to another Customer, the API should return:

```text
404 Not Found
```

rather than revealing:

```text
403 Forbidden
```

to the unauthorized customer.

This prevents confirming the existence of another customer's private ticket.

Agents and Administrators may receive conventional authorization errors where appropriate.

# 19. PATCH `/api/v1/tickets/{id}/status`

Changes ticket status.

### Access

AGENT  
ADMIN  
CUSTOMER only for permitted customer transition

### Request

```json
{
  "status": "IN_PROGRESS",
  "version": 3
}
```

`version` represents the version of the ticket the client last loaded.

### Allowed customer action

Customer:

```text
RESOLVED → IN_PROGRESS
```

for their own ticket.

Customers cannot perform arbitrary status transitions.

# 24. Optimistic Concurrency

All ticket mutation requests include the ticket version last seen by the client.

Example:

```json
{
  "status": "RESOLVED",
  "version": 6
}
```

If another user has modified the ticket and the current database version is `7`, the request must not silently overwrite the newer state.

Response:

```text
409 Conflict
```

```json
{
  "type": "/problems/stale-resource",
  "title": "Ticket has changed",
  "status": 409,
  "detail": "This ticket was modified by another user. Reload the ticket and try again.",
  "instance": "/api/v1/tickets/1042/status",
  "code": "STALE_RESOURCE"
}
```

The frontend should then refresh the ticket.

# 28. Comments on Closed Tickets

Attempting to comment on a CLOSED ticket returns:

```text
409 Conflict
```

```json
{
  "type": "/problems/ticket-closed",
  "title": "Ticket is closed",
  "status": 409,
  "detail": "Comments cannot be added to a closed ticket.",
  "instance": "/api/v1/tickets/1042/comments",
  "code": "TICKET_CLOSED"
}
```

There is no:

```text
PATCH /comments/{id}
```

and no:

```text
DELETE /comments/{id}
```

in MVP v1.

Comments are immutable.

# 35. Standard HTTP Status Codes

ResolveDesk should use HTTP status codes consistently.

| Status | Meaning |
|---|---|
| 200 | Successful retrieval/update |
| 201 | Resource successfully created |
| 204 | Successful operation with no body |
| 400 | Invalid request or validation |
| 401 | Authentication required/failed |
| 403 | Authenticated but unauthorized |
| 404 | Resource unavailable/not visible |
| 409 | Valid request conflicts with business state |
| 500 | Unexpected server failure |

---

# 36. Standard Error Format

Errors should use one consistent Problem Details-style structure.

Example:

```json
{
  "type": "/problems/validation-error",
  "title": "Validation failed",
  "status": 400,
  "detail": "One or more request fields are invalid.",
  "instance": "/api/v1/tickets",
  "code": "VALIDATION_ERROR",
  "fieldErrors": {
    "title": "Title must contain at least 3 characters.",
    "description": "Description must contain at least 10 characters."
  }
}
```

The `code` value provides a stable machine-readable identifier for the React application.

---

# 37. Error Codes

Initial error codes should include:

```text
VALIDATION_ERROR

AUTHENTICATION_REQUIRED
INVALID_CREDENTIALS
ACCOUNT_INACTIVE

ACCESS_DENIED
RESOURCE_NOT_FOUND

EMAIL_ALREADY_EXISTS

INVALID_STATUS_TRANSITION
INVALID_ASSIGNEE
TICKET_CLOSED
STALE_RESOURCE

AGENT_HAS_ACTIVE_TICKETS
LAST_ACTIVE_ADMIN

INTERNAL_ERROR
```

Frontend code should rely on stable `code` values rather than parsing human-readable messages.

# 40. Security Rules

The API must never trust client-submitted ownership information.

Examples:

Ticket creation must use:

```text
authenticatedUser.id
```

not:

```json
{
  "customerId": 17
}
```

Comment creation must use:

```text
authenticatedUser.id
```

not:

```json
{
  "authorId": 8
}
```

Ticket history actor must be derived from the authenticated operation.

---

# 41. Mass Assignment Protection

The API deliberately exposes narrow command endpoints.

For example:

```text
PATCH /tickets/1042/status
```

can modify status.

It cannot silently modify:

- customer;
- assignee;
- title;
- priority;
- closed timestamp.

Similarly:

```text
PATCH /tickets/1042/priority
```

modifies only priority.

There will be no generic endpoint such as:

```text
PUT /tickets/1042
```

accepting the entire Ticket object.

This reduces accidental or unauthorized field modification.

# 43. Suggested Spring Controller Boundaries

The HTTP controllers can map approximately to:

```text
AuthController

CurrentUserController
UserAdminController
AgentController

TicketController
TicketStatusController
TicketAssignmentController

CommentController
TicketHistoryController
```

This does not require creating a separate controller for every endpoint.

The important rule is that controllers remain thin.

Example responsibility:

```text
Controller:
parse HTTP request
validate DTO
obtain authenticated identity
call service
map response
```

Not:

```text
Controller:
decide business workflow
manipulate JPA entities
build audit history
decide status transition legality
```

Those belong lower in the application/domain layer.

# 44. Example End-to-End API Flow

A normal customer-to-resolution flow may look like:

```text
POST /auth/login
        │
        ▼
POST /tickets
        │
        ▼

        │
        ▼
GET /tickets
        │
        │ Agent
        ▼
PATCH /tickets/1042/assignee
        │
        ▼

OPEN → IN_PROGRESS
        │
        ▼

        │
        ▼
PATCH /tickets/1042/status
IN_PROGRESS → RESOLVED
        │
        │ Customer still has problem
        ▼
PATCH /tickets/1042/status
RESOLVED → IN_PROGRESS
        │
        ▼
... further work ...
        │
        ▼

        ▼

RESOLVED → CLOSED
```

Throughout the process:

```text

```

provides the immutable audit trail.

# 45. OpenAPI Documentation

The implemented Spring application should expose generated API documentation using OpenAPI.

The goal is for the contract to be inspectable through tooling such as Swagger UI.

However, generated documentation must reflect this agreed contract rather than replacing the planning process.

Annotations should document:

- request types;
- responses;
- status codes;
- authentication requirements;
- validation constraints.

# 48. API Acceptance Criteria

The API design is considered ready for implementation when:

- every MVP workflow has an endpoint;
- every endpoint has defined authorization;
- request ownership cannot be spoofed;
- mutation routes change only intended fields;
- status transitions remain domain-controlled;
- errors follow one format;
- pagination follows one format;
- ticket mutations account for concurrent changes;
- immutable resources have no edit/delete routes;
- customers cannot discover other customers' ticket data;
- DTOs rather than entities form the public contract;
- business conflicts use meaningful responses;
- the frontend can implement every required MVP screen using this API.
