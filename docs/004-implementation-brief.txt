# Implementation Brief

## Project Objective

Build **ResolveDesk**, a professional full-stack customer support ticket management application intended primarily as a software-engineering portfolio project.

The application should demonstrate the design and implementation of a realistic business workflow rather than functioning as a generic CRUD application.

ResolveDesk allows:

- Customers to register, authenticate, create support tickets, follow ticket progress, comment on active tickets, and reopen eligible resolved tickets.
- Support Agents to manage the support queue, assign tickets, change priority, update ticket status, communicate with customers, and review ticket history.
- Administrators to manage users and perform support operations.

The application must prioritize correct business behaviour, maintainability, security, testing, and clear architecture over feature quantity.

## Core Domain

The MVP contains four primary persistent domain entities:

- User
- Ticket
- Comment
- TicketHistory

Core ticket workflow:

```text
OPEN
  ↓
IN_PROGRESS
  ↓
RESOLVED
  ↓
CLOSED
```

Additional permitted transitions are defined in the Domain Model specification.

Ticket status must not be treated as an arbitrary editable field.

Status changes are business operations and must be validated by backend domain/service logic.

---

## Core Engineering Principles

The implementation must follow these principles:

### Backend authorization is authoritative

The frontend may hide unavailable controls, but authorization must always be enforced by Spring Security and/or backend business logic.

### Controllers remain thin

Controllers should handle HTTP concerns and delegate business behaviour to application/service logic.

### JPA entities are not API models

REST endpoints must use request and response DTOs.

### Business operations are explicit

Operations such as:

- assigning a ticket;
- changing status;
- changing priority;
- reopening a ticket;

must use dedicated business methods rather than arbitrary entity field updates.

### Audit history is reliable

Significant ticket changes must create immutable TicketHistory records in the same transaction as the underlying change.

### Core records are preserved

Tickets, comments, and ticket history are not hard-deleted in MVP v1.

Users are deactivated rather than deleted.

### Concurrency must be considered

Ticket updates use optimistic locking so that concurrent agent updates cannot silently overwrite one another.

## Development Approach

Do not attempt to generate the entire application in one pass.

Implement ResolveDesk incrementally using small, working vertical slices.

A recommended progression is:

```text
1. Repository and project scaffolding

2. Database configuration + Flyway

3. User domain and persistence

4. Authentication and authorization

5. Customer ticket creation

6. Customer ticket list

7. Ticket detail

8. Agent ticket queue

9. Ticket assignment

10. Status workflow

11. Priority management

12. Comments

13. Ticket history

14. Search / filtering / sorting / pagination

15. Administration

16. Integration and security testing

17. Docker and CI

18. UI polish and documentation
```

Each stage should leave the application in a working state.

## Testing Expectations

Testing is part of implementation, not a final cleanup phase.

Important business rules should receive automated tests as they are introduced.

High-priority scenarios include:

```text
Customer can create a ticket.

Customer cannot access another customer's ticket.

Customer cannot assign a ticket.

Customer cannot change priority.

Agent can assign an eligible ticket.

Inactive user cannot authenticate.

OPEN can transition to IN_PROGRESS.

OPEN cannot transition directly to CLOSED.

IN_PROGRESS can transition to RESOLVED.

RESOLVED can be reopened.

CLOSED tickets cannot receive comments.

Status changes create history records.

Assignment changes create history records.

Concurrent stale updates are rejected.

Agent with active assigned tickets cannot be deactivated.

Final active administrator cannot be removed/deactivated.
```

Tests should focus on meaningful behaviour rather than maximizing coverage percentage.

## Definition of Done

ResolveDesk MVP is complete when a user can successfully perform the full workflow:

```text
Customer registers
        ↓
Customer logs in
        ↓
Customer creates ticket
        ↓
Agent sees ticket in support queue
        ↓
Agent assigns ticket
        ↓
Agent moves ticket to IN_PROGRESS
        ↓
Customer and agent communicate
        ↓
Agent resolves ticket
        ↓
Customer may reopen if necessary
        ↓
Agent eventually resolves and closes ticket
        ↓
Entire lifecycle remains visible in ticket history
```

In addition:

- permissions must be enforced server-side;
- invalid workflow operations must be rejected;
- important business behaviour must be tested;
- database creation must be reproducible through Flyway;
- the project must be runnable from documented local setup instructions;
- the repository must not contain secrets;
- frontend and backend must integrate through the documented REST API.
